## 一、先说明数据口径

这次没有把旧的 `height` 字段直接改成公斤。原因是旧身高历史是 `172~175 厘米`，直接改单位会变成“175 公斤”的假数据，也会让旧记录和新记录混在一起。

采用的做法：

- 新增独立指标 `muscle`，名称“肌肉重量”，单位“公斤”，范围 `20~120`，正常按 `1` 位小数显示。
- 旧 `height` 继续保存在本机 JSON 和服务端数据库里，但不进入新界面、不写入新值、不参与新趋势。这样旧厘米历史不会冒充公斤。
- 体脂率继续使用独立的 `body_fat` 记录体系，不和 `muscle`、`height` 混存。
- 新客户端只展示 `muscle`；旧客户端仍能同步 `height`，互不破坏。

### 3.1 测量桥

| 文件 | 变更 |
|---|---|
| `measure/OkokBridgeContract.kt` | 新增日刻/模块共用契约；`creatorPackage` 必须是 `com.beike.daytally` |
| `measure/OkokMeasurementPolicy.kt` | 新增纯规则：30 分钟会话、`weight × percent / 100`、体脂/肌肉范围、1 位小数、失效安全 |
| `measure/MeasurementBridge.kt` | 新增：Hook `MainActivity.onCreate(Bundle)` / `onNewIntent(Intent)`，在 `chain.proceed()` 之前捕获 `EXTRA_RESULT_PENDING_INTENT` 与 `EXTRA_SESSION_ID`；Hook `BluetoothUpScaleActivity.startReportActivity(WeightEntity)`，反射读 `getWeight/getAxunge/getDbMuscle/getMuscle`，换算后用 PendingIntent 回传；回传后清会话 |
| `ModuleEntry.kt` | 安装测量桥；保留原广告规则安装路径 |

测量桥的边界：

- 不修改 OKOK 登录、账号、会员、服务器请求、测量算法。
- 不伪造数值；只把 OKOK 自己生成的 `WeightEntity` 结果换算成日刻记录。
- 回传 PendingIntent 用 `FLAG_UPDATE_CURRENT or FLAG_MUTABLE`，因为 OKOK 适配层需要在 `send()` 时填入本次结果；模块侧校验 `creatorPackage`，日刻侧 Receiver 是 `exported=false` 的显式接收器。
- 会话 30 分钟过期；OKOK 进程被杀导致会话丢失时，日刻侧走失败兜底，不静默写错数据。
